# Plan: 0.45.0 — Switch firmware and keys

Milestone 0.45.0, umbrella issue #12 (sub-issues #29–#32 and the ones listed below). Plan §4 Phase 7, decision D7.
Status: **plan; decisions made 2026-11-10; queue design (§3) confirmed; device facts recorded in §6 (they change decision 2, see there).**

## 1. Goal and non-goals

**Goal.** The System page lists the Switch firmware and key files RomM hosts (name, size, downloaded or not), lets
the user choose a firmware version, downloads through the normal download queue (pause/resume/cancel/reorder like a
ROM) and puts the files where Eden, yuzu and Ryujinx read them. The firmware callables stop answering
`not_implemented` (`src/api/unportedCallable.ts` loses its firmware entries).

**Non-goals.** No auto-install into the emulator (plan §7): the UI says where the file is and that it is installed from
the emulator's own menu. No per-platform BIOS (0.80/0.90). No port of the Python registry logic (it models RetroArch
cores and has no Switch entry); Python reference commit `580680864e89af50c376dc946d12cf35cee7f808`
(`services/firmware.py`, `domain/firmware_paths.py`) is used for RomM API handling only.

## 2. Decisions (Patrick, 2026-11-10)

| # | Decision |
| - | -------- |
| 1 | Firmware goes through **the same durable download queue** as ROMs: one list, one pause click, one transfer slot (D5). The queue is generalized to job kinds (§3). |
| 2 | *(premise changed by the device facts in §6; adapted proposal there, needs a yes)* The firmware **store lives on the same filesystem as `<Emulation>`** (`<storagePath>/Emulation/.romm-sync/firmware/`), so hard links into `bios/<emulator>/` work on Deck internal and SD card. A copy fallback remains for filesystems without hard links (e.g. exFAT). Uninstalling the plugin leaves the store behind; the docs say so. |
| 3 | **`title.keys` are required** (with `prod.keys`). The **firmware version is selectable** (default: newest RomM has); "Download required" fetches keys + the selected version. |

## 3. Queue generalization (needs confirmation)

Today the queue is ROM-shaped: `download_jobs.rom_id` is the primary key, `DownloadService` (≈1,400 lines, 183 `rom_id`
mentions) mixes generic scheduling with ROM-only work (sibling supersede, extraction, install record, launch baking),
events and the frontend key everything by `rom_id`.

**Phase A — refactor, no behavior change (own PR, ROM tests stay green):**

- `JobKey { kind: Rom | Firmware, id }` replaces the bare `rom_id` inside `DownloadService`, the job aggregate and the
  repository. Migration `014_download_job_kinds.sql` rebuilds `download_jobs` with `kind TEXT NOT NULL DEFAULT 'rom'`
  and `PRIMARY KEY (kind, item_id)`; existing rows become `kind = 'rom'`.
- The scheduler (slot, positions, move-to-front, pause/cancel/shutdown, persistence, reconcile, retry/phase reporting)
  stays one implementation. The per-kind handler abstraction (`prepare`, `request`, `finish`, `cleanup`) is introduced
  **in Phase B**, when the second implementation exists; Phase A only threads the key through (a handler extracted
  with one implementation would be a guess). In Phase A a request for kind `firmware` answers `unsupported_kind`.
- Callables keep their names and ROM arity. `start_download`, `pause_download`, `resume_download`, `cancel_download`,
  `move_to_front` take an optional second argument `kind` (default `"rom"`); firmware is started with
  `start_download(firmware_id, "firmware")`. `get_download_queue` and the `download_*` events carry `kind`; ROM frames
  keep `rom_id`, firmware frames carry `firmware_id`.
- Frontend: Phase A only adds the optional `kind` to the types. The store key `(kind, id)` and `DownloadQueue`
  rendering both kinds come with Phase B, where they can be tested against real firmware items; the game-page button
  already ignores frames without its `rom_id`.

**Phase B — firmware handler:** resolves the file from the cached list, targets the store path, verifies the MD5
RomM reports, links into the emulator folders, records `downloaded_bios`, emits the same progress/phase frames
(waiting/retrying, pause, resume).

**Risk and mitigation.** This touches the queue we just released as v0.40.0. Phase A lands alone, behind the existing
suites (≈40 service tests, the real-binary integration tests, the cached-ZIP tests) plus mutation spot checks, and is
released as an rc before Phase B builds on it.

## 4. Switch firmware domain (`domain/switch_firmware.rs`, pure)

- **Classification** by RomM `file_name`: `prod.keys`, `title.keys` → keys (required); `Firmware <x.y.z>.zip` (and the
  name variants seen on the real server) → firmware, version parsed; anything else → unknown.
- **Version selection:** versions sorted semantically; default newest; the choice is a plugin setting
  (`switch_firmware_version`) and the UI lists the versions RomM has.
- **Destinations:** a table emulator → keys directory (§6), plus the firmware archive directory
  `<Emulation>/bios/switch/`, every path through `safe_join`. The keys directories are verified on the Deck; Bazzite is open.
- **Status per file:** not downloaded · downloaded · linked into (emulator list) · hash mismatch · unverified (RomM
  reports no MD5).

## 5. Service, data and UI

- `FirmwareService`: list from `GET /api/firmware` with the existing `firmware_cache` (1 h TTL, offline fallback to
  the cached list), status per file, and the queue handler of Phase B. The downloaded record uses the existing
  `downloaded_bios` table (no new table).
- Download order of operations (adapted proposal, §6.3): disk-space preflight → `<destination>.tmp` → hash check → atomic
  rename → copy to the other emulators' key directories → record. A failed download or a mismatching hash never
  replaces an existing good file, and a differing existing key file is only replaced by an explicit action (the old
  file is kept as `.romm-backup`).
- Callables: `get_firmware_status`, `download_all_firmware`, `download_required_firmware` keep their names; response
  shapes are redefined with the frontend in the same PR. Version selection is saved through the existing settings path.
- UI: the System page becomes a small Switch firmware view: file rows with size and status, a version selector,
  Download required / Download all, progress in the Downloads list, and the hint "Saved to … — install it from Eden's or
  Ryujinx's own Install Firmware menu".

## 6. Device facts (Steam Deck, recorded 2026-11-10 in #69)

**RomM `GET /api/firmware?platform_id=9`** returns five Switch files, `file_path: "bios/Switch"` (capital S, so match by
`platform_id`, not by a lower-cased path slug): `console.keys` (451 B), `Firmware.23.0.1.zip` (340,422,248 B),
`key_retail.bin` (160 B), `prod.keys` (16,025 B), `title.keys` (1,224 B). Each entry has `md5_hash`, `sha1_hash`,
`crc_hash`, `file_size_bytes`, `is_verified` and `missing_from_fs`. Firmware versions are named `Firmware.<x.y.z>.zip`.

**Where the emulators read keys** (all on internal storage, none under `Emulation/bios`):

| Emulator | Keys directory | Present on the Deck |
| -------- | -------------- | ------------------- |
| Eden | `~/.local/share/eden/keys/` | `prod.keys`, `title.keys`, `title.keys_autogenerated` (the emulator's own) |
| yuzu | `~/.local/share/yuzu/keys/` | `prod.keys`, `title.keys`, `title.keys_autogenerated`, `readme.txt` |
| Ryujinx | `~/.config/Ryujinx/system/` | `prod.keys`, `title.keys`, `console.keys`, `key_retail.bin`, `Profiles.json`, `old-keys-backup/` |

**Filesystem:** `Emulation` is on the SD card, **ext4** (`/dev/mmcblk0p1`), so hard links work there; the key
directories are on the internal drive (a different filesystem).

**What follows**

1. The D7 destination table (`Emulation/bios/<emulator>/…`) was wrong: keys belong in the three directories above.
   Hard links from a store on the SD card into `$HOME` would fail with `EXDEV`, so **decision 2 does not do what it was
   meant to**.
2. Keys are tiny (≤16 KB): copy them, no links. Only the 340 MB firmware archive is large, and the plugin never installs
   it (the user picks it in the emulator's *Install Firmware* dialog).
3. **Adapted proposal for decision 2 (needs Patrick's yes):** no separate "firmware store". Download to
   `<destination>.tmp` next to the final path, verify the SHA-1, rename atomically (same filesystem by construction), then
   copy to the other emulators' key directories. Keys go to the three directories above; the firmware archive goes to
   `<Emulation>/bios/switch/` on the SD card (large file, easy to find in the emulator's file dialog). Hard links and the
   copy-fallback question disappear.
4. **Never silently replace a user's working keys.** The Deck's own `prod.keys` (14,612 B in Eden/Ryujinx, 15,039 B in
   yuzu) differs from RomM's (16,025 B). Per file the status is `matches RomM` / `present, differs from RomM` /
   `missing`; a differing file is not overwritten by default, an explicit *Replace* moves the old one to a
   `.romm-backup` first (the same rule as save quarantine). `title.keys_autogenerated` is never touched.
5. Which keys each emulator needs: Eden and yuzu `prod.keys` + `title.keys`; Ryujinx the same, and optionally
   `console.keys` and `key_retail.bin` (RomM hosts them). Required (decision 3): `prod.keys` + `title.keys`.
6. Still unverified: the same layout on the Bazzite PCs (Eden/Ryujinx there may be Flatpaks with other data paths).
   Check before the rc is tested on them.

fake RomM (download, hash match/mismatch, interruption and resume across a restart, existing file never clobbered,
link and copy fallback, offline list), the queue refactor under the existing suites, frontend (list, version

## 9. Definition of done

The System page lists the Switch firmware and keys, the chosen version downloads through the shared queue and can be
paused with one click, the files are where the emulator reads them, a game that needed the keys starts, #12, #29–#32
and #69–#71 are closed, the firmware `unportedCallable` entries are gone, and CI, the release dry run and the device
test are green.

## 10. Progress notes

- **Hash:** RomM publishes `md5_hash`, `sha1_hash` and `crc_hash`; the plan said MD5, but the backend's crypto crate (`ring`)
  has no MD5, so comparisons use **SHA-1** (stronger, and already in RomM's answer).
- **0.41.0 scope** (first release toward 0.45.0, Patrick wanted download and version choice in it): the firmware
  list (#29), the selectable version (#71) and the downloads through the shared queue (#30, #31 as adapted in §6):
  `get_firmware_status`, `save_firmware_version`, `download_required_firmware`, `download_all_firmware` are ported
  (`domain/switch_firmware.rs`, `services/firmware.rs`, the firmware path in `services/downloads.rs`). Keys are
  verified (SHA-1), stored for the first emulator that lacks them and copied to the others; archives go to
  `<Emulation>/bios/switch/`. **Not in 0.41.0:** an explicit "Replace" for a key file that differs from RomM's (it is
  reported and kept), the `downloaded_bios` table (state is derived from disk), the Bazzite check, the user-guide rewrite (#32).
- **0.42.0 scope:** the explicit "Replace" for a key file that differs from RomM's (`replace_firmware_key`, button + confirm
  dialog per emulator on the System page). Inline and verified, the old file is kept as `.romm-backup`; closes the last
  part of #31.
