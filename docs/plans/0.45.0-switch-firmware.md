# Plan: 0.45.0 — Switch firmware and keys

Milestone 0.45.0, umbrella issue #12 (sub-issues #29–#32 and the ones listed below). Plan §4 Phase 7, decision D7.
Status: **plan, decisions made 2026-11-10; the queue design (§3) still needs Patrick's confirmation before code.**

## 1. Goal and non-goals

**Goal.** The System page lists the Switch firmware and key files RomM hosts (name, size, downloaded or not), lets
the user choose a firmware version, downloads through the normal download queue (pause/resume/cancel/reorder like a
ROM) and puts the files where Eden, yuzu and Ryujinx read them. The firmware callables stop answering
`not_implemented` (`src/api/unportedCallable.ts` loses its firmware entries).

**Non-goals.** No auto-install into the emulator (plan §7): the UI says where the file is and that it is installed from
the emulator's own menu. No per-platform BIOS (0.80/0.90). No port of the Python registry logic (it models RetroArch
cores and has no Switch entry); Python reference commit `580680864e89af50c376dc946d12cf35cee7f808`
(`services/firmware.py`, `domain/firmware_paths.py`) is used for RomM API handling only.

## 2. Decisions (Patrick, 2026-11-10)

| # | Decision |
| - | -------- |
| 1 | Firmware goes through **the same durable download queue** as ROMs: one list, one pause click, one transfer slot (D5). The queue is generalized to job kinds (§3). |
| 2 | The firmware **store lives on the same filesystem as `<Emulation>`** (`<storagePath>/Emulation/.romm-sync/firmware/`), so hard links into `bios/<emulator>/` work on Deck internal and SD card. A copy fallback remains for filesystems without hard links (e.g. exFAT). Uninstalling the plugin leaves the store behind; the docs say so. |
| 3 | **`title.keys` are required** (with `prod.keys`). The **firmware version is selectable** (default: newest RomM has); "Download required" fetches keys + the selected version. |

## 3. Queue generalization (needs confirmation)

Today the queue is ROM-shaped: `download_jobs.rom_id` is the primary key, `DownloadService` (≈1,400 lines, 183 `rom_id`
mentions) mixes generic scheduling with ROM-only work (sibling supersede, extraction, install record, launch baking),
events and the frontend key everything by `rom_id`.

**Phase A — refactor, no behavior change (own PR, ROM tests stay green):**

- `JobKey { kind: Rom | Firmware, id }` replaces the bare `rom_id` inside `DownloadService`, the job aggregate and the
  repository. Migration `014_download_job_kinds.sql` rebuilds `download_jobs` with `kind TEXT NOT NULL DEFAULT 'rom'`
  and `PRIMARY KEY (kind, item_id)`; existing rows become `kind = 'rom'`.
- The scheduler (slot, positions, move-to-front, pause/cancel/shutdown, persistence, reconcile, retry/phase reporting)
  stays one implementation. ROM-only work moves behind a per-kind handler (`prepare`, `request`, `finish`, `cleanup`);
  the existing ROM behavior is the first handler, unchanged.
- Callables keep their names and ROM arity. `start_download`, `pause_download`, `resume_download`, `cancel_download`,
  `move_to_front` take an optional second argument `kind` (default `"rom"`); firmware is started with
  `start_download(firmware_id, "firmware")`. `get_download_queue` and the `download_*` events carry `kind`; ROM frames
  keep `rom_id`, firmware frames carry `firmware_id`.
- Frontend: `DownloadItem` gets `kind`; the store key becomes `(kind, id)`; `DownloadQueue` renders both kinds; the
  game-page button already ignores frames without its `rom_id`.

**Phase B — firmware handler:** resolves the file from the cached list, targets the store path, verifies the MD5
RomM reports, links into the emulator folders, records `downloaded_bios`, emits the same progress/phase frames
(waiting/retrying, pause, resume).

**Risk and mitigation.** This touches the queue we just released as v0.40.0. Phase A lands alone, behind the existing
suites (≈40 service tests, the real-binary integration tests, the cached-ZIP tests) plus mutation spot checks, and is
released as an rc before Phase B builds on it.

## 4. Switch firmware domain (`domain/switch_firmware.rs`, pure)

- **Classification** by RomM `file_name`: `prod.keys`, `title.keys` → keys (required); `Firmware <x.y.z>.zip` (and the
  name variants seen on the real server) → firmware, version parsed; anything else → unknown.
- **Version selection:** versions sorted semantically; default newest; the choice is a plugin setting
  (`switch_firmware_version`) and the UI lists the versions RomM has.
- **Destinations:** a table emulator → keys dir, firmware dir under `<Emulation>/bios/<emulator>/…`, every path through
  `safe_join`. **Exact folders are placeholders until verified on a device** (§6).
- **Status per file:** not downloaded · downloaded · linked into (emulator list) · hash mismatch · unverified (RomM
  reports no MD5).

## 5. Service, data and UI

- `FirmwareService`: list from `GET /api/firmware` with the existing `firmware_cache` (1 h TTL, offline fallback to
  the cached list), status per file, and the queue handler of Phase B. The downloaded record uses the existing
  `downloaded_bios` table (no new table).
- Download order of operations: disk-space preflight → `.tmp` in the store → hash check → atomic rename in the store →
  hard link into each installed emulator's folder (copy if links are unsupported) → record. A failed download or a
  mismatching hash never replaces an existing good file.
- Callables: `get_firmware_status`, `download_all_firmware`, `download_required_firmware` keep their names; response
  shapes are redefined with the frontend in the same PR. Version selection is saved through the existing settings path.
- UI: the System page becomes a small Switch firmware view: file rows with size and status, a version selector,
  Download required / Download all, progress in the Downloads list, and the hint "Saved to … — install it from Eden's or
  Ryujinx's own Install Firmware menu".

## 6. Verify on a device (blocks the destination table)

1. RomM's real response for the Switch platform: `file_path`, `file_name`, `md5_hash`, sizes, version naming (one
   `curl` with your own token; paste the result without the token).
2. Where each emulator reads keys and firmware under EmuDeck: `ls -la` / `readlink -f` for
   `Emulation/bios/{yuzu,eden,ryujinx}`, `~/.local/share/{eden,yuzu}/keys`, `~/.config/Ryujinx/system`.
3. The filesystem of the SD card (`findmnt -T <storagePath>/Emulation`) and whether a hard link works there.

fake RomM (download, hash match/mismatch, interruption and resume across a restart, existing file never clobbered,
link and copy fallback, offline list), the queue refactor under the existing suites, frontend (list, version
selection, progress in the shared queue, offline, hash mismatch), and mutation spot checks on the safety rules.

## 9. Definition of done

The System page lists the Switch firmware and keys, the chosen version downloads through the shared queue and can be
paused with one click, the files are where the emulator reads them, a game that needed the keys starts, #12, #29–#32
and #69–#71 are closed, the firmware `unportedCallable` entries are gone, and CI, the release dry run and the device
test are green.
